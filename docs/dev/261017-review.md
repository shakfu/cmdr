# Review: cmdr

**Date:** 2026-10-17 **Version reviewed:** `0.1.0` (git `a69dff7`, branch `main`) **Scope:** full source (`src/`, `thirdparty/linenoise`), tests, build system, docs, examples, and git history.

---

## Executive summary

cmdr is a small, single-binary C11 REPL and scripting tool for composing text/list transformations with an explicit shell-like pipeline language. It is in excellent shape for a 0.1.0 release: the code is dense but readable, error handling is careful, the test suite is unusually good (including PTY-driven interaction tests), and the design history is documented in-tree.

I built the project, ran the full test suite (31/31 pass), rebuilt with ASan+UBSan (all tests pass, 0 warnings), and ran valgrind (0 errors, 0 definite leaks). I found no correctness bugs in the code I exercised. The findings below are mostly sharp edges, minor inconsistencies, and suggestions, ordered roughly by importance.

---

## Overview

- **What it is.** A command REPL where `a | b x` runs `a`, then calls `b`
  with the result as its first argument. Values are text, lists, or blocks (`{ ... }` pipelines). Commands are either C primitives (`src/primitives.c`), application commands (`src/main.c`), or composed defs (`src/prelude.cmdr`, embedded at build time).

- **Language of implementation.** ISO C11, POSIX 200809 (`getline`, `open_memstream`, `posix_spawn`, `fstatat`, `tmpfile`), CMake 3.16+. ~1,800 lines of project C across 4 translation units, plus a vendored linenoise (~3,550 lines).

- **Extras.** Interactive line editing with syntax highlighting, completion, and history; `-c` one-shot mode; script files; piped stdin; `load`; `--user` prelude; `--version`.

- **Size.** Binary ≈ 368 KB (RelWithDebInfo).

## Architecture

The code is organized around a small public API (`src/cmdr.h`): values, a command registry built of lookup layers (`struct cmdr` with parent chains), and four entry points (`cmdr_eval`, `cmdr_call`, `cmdr_run`, `cmdr_block_arity`). The interesting parts:

- **Compile-then-run.** A pipeline parses and compiles once, before any stage runs: command names are resolved, `$name` references are rewired to environment slots, and nested blocks compile with their enclosing line. This means syntax/name errors are reported *before* any effects happen — a nice property for a tool with side effects (`read`, `write`, `run`).

- **Lexical scope with capture.** Blocks capture the values of enclosing names at definition; `def` produces a closure that survives its defining session. Compiled code is reference-counted, so copies of a block share one compile (measured 0.023s → 0.010s per-call in `docs/dev/blocks.md`).

- **Bounded recursion.** Call depth is capped at 128 (guards against cycles in composed commands) and value nesting at 1024; both are exercised by tests. This is the kind of defensive design small recursive interpreters usually skip.

- **Exact block arity.** A block takes exactly the arguments it declares, and declared-but-unused parameters are compile errors. This converts an entire class of silent wrong answers (e.g., `try` swallowing a missing input) into loud, early errors. The design record in `docs/dev/blocks.md` shows this was a deliberate choice over alternatives (P/L/N prototypes).

- **`run` implementation.** Uses `tmpfile` + `F_DUPFD_CLOEXEC` (fd ≥ 3) and files rather than pipes, so a child that writes before reading cannot deadlock and the dup2 in the child cannot close cmdr's own stdio. Nice.

## What is done well

- **Error reporting.** Errors carry call chains for defs (`outer: inner: equals: ...`), and line/column context is threaded through scripts and the prelude (`prelude.cmdr:2: ...`). Mismatches (`CMDR_MISMATCH`, status 2) are cleanly distinguished from real errors, which lets `keep`/`not`/`try` treat only a mismatch as false.

- **Tests.** 31 methods covering values, effects, recovery, lexical definitions, prelude behavior, limits, escapes, and — notably — a PTY harness that types into a real terminal session to test the editor, pasting, Ctrl-C, completion, and history. One CTest test per method with `configure_depends` so new tests register on reconfigure automatically.

- **Documentation.** The README is thorough, accurate (I spot-checked many claims), and matches observed behavior. In-tree design records (`docs/dev/minimal.md`, `blocks.md`, `compose-ng.md`) preserve reasoning and measurements that would otherwise be lost.

- **Build hygiene.** Vendored linenoise is pinned with version and patch notes in `thirdparty/linenoise/VENDOR`; a historical `strdup`/`fdopen` truncation bug is guarded with `-Werror=implicit-function-declaration`. The prelude is embedded via hex with a `COPYONLY` configure step, so reconfiguring doesn't force rebuilds. Blank/comment handling, `quit` detection, and banner behavior are all covered by tests.

- **Error-model consistency.** "A failed stage stops the pipeline before
  later effects" is tested (`run false | write` leaves no file), and
  pre-validation means unknown names in a later block never cause partial effects.

## Findings

### 1. Quoted strings cannot span lines in scripts or stdin (medium)

`-c PIPELINE`, `load`, and the embedded prelude evaluate a whole string, and the lexer happily treats a newline inside double quotes as whitespace. But the script/stdin driver (`run()` in `src/main.c`) splits input at physical
newlines *before* parsing, and only joins lines ending in an unescaped `|`.
The same source behaves differently by mode:

```sh
$ echo 'text "x
y" | count' | cmdr          # unclosed quote
$ cmdr -c 'text "x
y" | count'                    # 2
```

For a value that contains a newline, the `\n` escape works in all modes (`text "x\ny\n"`), so this is a limitation rather than a bug — but the error message ("unclosed quote") is actively misleading, since the quote *is* closed later in the file. Two reasonable fixes, in order of effort:

- Document it: "quotes cannot span lines; use `\n`" — one sentence in the README's Composition section.

- Or make `run()` continue a line when it ends inside an open quote (a quote-tracking wrapper around the existing `continues()` logic), matching what `cmdr_eval` already accepts.

### 2. `write`/`append` of a block value writes bare source (low)

`cmdr_render` prints a block as `{...}` — its source only, no captured values, and no trailing newline for list/block rendering. Writing a block to a file therefore silently loses its captured environment and may produce a file without a trailing newline. Blocks are a first-class value here, so the behavior is defensible (source is the only faithful serialization), but it
isn't documented and would surprise someone doing `def c { ... } | write
note.txt`. At minimum, note it in the `write` row of the README table.

### 3. Session defs are never freed (low, by design but worth knowing)

Each `def` allocates a permanent layer node; there is no `undef`, only shadowing. A long-lived REPL session that defines many commands grows unboundedly. Bounded and documented in a comment ("Layers are never freed"), so this is a design choice — but with 1000+ unique defs, memory becomes noticeable. Consider a `def`-cap or an `undef`/re-def (redefining a name could reuse its node) if long sessions matter.

### 4. `run`'s stderr is always inherited (low)

`run`/`run-in` capture stdout only; child stderr goes to cmdr's stderr
directly. In a pipeline `run cmd | filter err`, the child's stderr bypasses
the pipeline entirely. That is a reasonable first cut (many shell pipelines want this), but it's undocumented and there's no `run-e` variant to capture stderr as a value. Document the behavior, or add a flag/command later.

### 5. History is saved to disk after every command (low)

`editor_remember` calls `linenoise_history_save` per line. On a slow filesystem or a session typing fast, that is unnecessary I/O per keystroke-Enter. A deferred save (e.g., on close and periodically) would be an easy win, and avoid partial history on crash.

### 6. Long path error prefixes can truncate (cosmetic)

`run()` formats `where` into a fixed 4096-byte buffer with `snprintf`; very deep script paths truncate the `FILE:LINE:` prefix silently. Cosmetic only.

### 7. `example/mforth.c` is orphaned (cosmetic)

A self-contained minimal Forth interpreter (single file, ~150 lines) lives in `example/` but is not referenced by the README, build, or docs. If it's meant to show "how to build a tool like this", tie it in (a paragraph in the README or a `docs/dev/` note); otherwise it reads as leftover scaffolding.

### 8. Vendored linenoise dominates the tree (maintenance note)

`thirdparty/linenoise` is ~3,550 lines against ~1,800 lines of project C — roughly two-thirds of the vendored surface is for syntax themes cmdr doesn't use (the VENDOR file says so). The pinning and patch notes are exemplary; if the fork drifts, options are trimming to a minimal subset or moving to the builder's own terminal handling. Not urgent — just noting the size asymmetry the maintenance burden implies.

### 9. Minor nits

- `cmdr_error` returns 1 unconditionally, but several primitives use `return cmdr_error(...), CMDR_MISMATCH;` (comma operator) to set the error and return mismatch. Correct and terse, but obscures intent; a tiny helper (`return mismatch(error, "...")`) would read better.

- `compare()` builds its error message even on success paths... it doesn't — the message construction is inside the failure branch; fine as written.

- The global `static unsigned depth` call-depth counter in `cmdr_call` is technically thread-hostile; fine for this single-threaded binary, worth a comment (it does have one).

- No install rules or `#!/usr/bin/env cmdr` installation story despite shebang scripts being supported; a `make install` (or even a documented `install -m755 build/cmdr $PREFIX/bin`) would complete the picture.

- The unused `example/` and `janet`/`minimal` git branches are historical; `docs/dev/compose-ng.md` explicitly still describes the pre-block design, which is fine (it says so) but could confuse a reader expecting current docs.

## Verification I couldn't do

- Non-Linux/macOS ports (Windows/mingw): not tested here; the code is POSIX-2008-specific by design and the README says so.

- Very large inputs beyond the test suite's 20,000-token line regression (memory behavior looks linear; no attempt to exhaust it).

- Compile under clang or with `-O0`/different sanitizer combos (only gcc + ASan/UBSan exercised).

## Verdict

**Approve / release-quality.** cmdr 0.1.0 does what it says, says what it does, and tests both. The single most valuable improvement is documenting or fixing the multiline-quote inconsistency (finding 1); everything else is polish. For a 1,800-line C program, the combination of design discipline (three prototype variants compared in `docs/dev/blocks.md`), defensive engineering (bounded recursion, exact arity, pre-validation), and genuine interaction tests is far above the norm.
